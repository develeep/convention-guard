## 왜 필요한가

N+1 쿼리, 계층 경계, "A 가 있으면 B 가 필요"가 함수 흐름에 달린 경우처럼 **코드 모양이 아니라 의미**를 봐야 판정되는 컨벤션이 있습니다. 정규식은 이런 코드를 후보로 좁힐 수는 있어도 판정은 못 합니다.

```php
$orders = Order::query()->with('items')->get();   // 이 줄이 있으면 VALID
foreach ($orders as $order) {
    $order->items->count();                        // 정규식은 둘을 구분 못 함
}
```

## 왜 전부 맡기지 않는가

| 문제 | 내용 |
|---|---|
| 비용 | Stop 은 매 턴 발생합니다. 무조건 판정하면 턴마다 LLM 호출 |
| 지연 | 도구를 쓰는 판정은 수십 초 |
| 비결정성 | 같은 코드에 다른 판정 |
| 수렴 실패 | 고칠 때마다 새 지적 — 검증 루프가 끝나지 않음 |

그래서 **결정론 게이트를 통과한 후보만**(정규식 신호가 없는 규칙은 [파일 글롭](#파일-글롭-상시-판정)에 든 파일의 판정 단위만), **판정 기록이 없는 코드만**, **함수 하나 분량의 컨텍스트로** 판정합니다.

## 흐름

```
Stop
 └ semantic_review 규칙의 detect 로 후보 탐지     후보 0건 → 끝 (AI 호출 없음)
   (when_code_added 규칙은 글롭에 든 파일의 판정 단위)
    └ 후보마다 컨텍스트 팩 + context_hash / related_hash
       └ 판정 캐시 조회 (rule:file:review_hash)
          ├ VALID / FALSE_POSITIVE → 제외
          ├ VIOLATION              → 결정론 지적처럼 차단 메시지에 포함
          └ 없음                   → 판정 배치 저장 (참조 <db 경로>#<id>)
             └ 차단 메시지: "convention-guard:convention-reviewer 에이전트에게
                            python3 .../review.py show <배치> 를 전달하세요"
                └ 메인 에이전트가 서브에이전트 호출
                   └ 리뷰어: show → 판정 → review.py record → 위반만 한 줄씩 응답
                      └ 메인 에이전트: VIOLATION 만 수정 → Stop → 검증
```

메인 에이전트의 컨텍스트에 들어가는 것은 명령 한 줄과 리뷰어의 짧은 응답뿐입니다. 컨텍스트 팩과 리뷰어가 읽은 코드는 서브에이전트 안에서 끝납니다.

설정: `semantic_review.enabled: true` (레포 config 또는 userConfig). 의미 판정 규칙이 있는 프리셋(`architecture`, `performance`, `layering`, 또는 `laravel` 의 N+1)이 활성이어야 합니다.

## 최소 충분 컨텍스트

규칙이 필요한 조각을 고르고, 조각마다 줄 예산이 있습니다.

| 조각 | 내용 | 상한 |
|---|---|---|
| `current_function` | 후보를 감싸는 이름 있는 함수·메서드. 길면 머리·후보 주변·꼬리만 | 80줄 |
| `snippet` | 후보 ±5줄 (함수를 못 찾으면 ±30줄로 대체) | |
| `imports` | 파일 상단의 import 문(언어별 패턴, 괄호가 닫힐 때까지 이어 읽음). 주석·문자열 안과 클래스 같은 블록 안(PHP trait `use`)은 제외 | 30줄 |
| `changed_hunks` | 같은 파일에서 이번 변경이 추가한 다른 줄 | 20줄 |
| `related_files` | 함수 안의 심볼(예: `Order::query`)로 찾은 파일의 앞부분 | 파일당 60줄, 최대 2개 |

- 규칙별 상한 `semantic_review.max_context_lines`, 배치 전체 상한 `semantic_review.context_budget_lines`
- 한 배치의 후보 수 상한 `semantic_review.max_candidates`. 넘치는 후보는 다음 판정으로 미룹니다
- 판정 단위는 함수입니다. 같은 함수 안에서 같은 규칙에 걸린 후보들은 한 질문(판정 하나)이 되고, 배치 항목은 그 후보들의 줄을 모두 나열합니다. 리뷰어는 그중 하나라도 위반이면 VIOLATION 으로 답합니다
- 잘린 곳에는 `… N줄 더 — 필요하면 Read` 가 붙습니다. 리뷰어는 판정에 꼭 필요할 때만, 후보당 최대 3번 더 읽습니다

함수 경계는 구조 엔진(tree-sitter)이 찾습니다. 지원 언어는 js/ts/tsx, php, Blade, Python 입니다. 엔진이 없거나 파일이 파싱되지 않으면 함수 영역 없이 후보 주변 ±30줄을 보내고 `함수 경계 미확인` 이라고 적습니다. `for (...) {` 같은 제어문은 함수로 보지 않습니다. 메서드와 람다는 함수로 봅니다. 다만 반복 메서드에 넘긴 콜백(`$orders->each(function ($o) {`, `xs.forEach(x => {`)은 판정 단위가 아니고, 그 바깥 함수가 단위입니다. 루프 위의 `with()` 같은 판정 근거가 바깥 함수에 있기 때문입니다.

## 판정 캐시와 중복 방지

캐시 키는 `rule:file:review_hash` 이고, `review_hash` 는 **그 판정이 의존한 것 전부**를 하나로 접은 지문입니다.

| 조각 | 내용 | 바뀌면 |
|---|---|---|
| `definition_hash` | 규칙의 `detect` 게이트 + `semantic_review` (instruction, context, max_context_lines) | 질문 자체가 달라졌으므로 재판정 |
| `context_hash` | 주 영역 — 감싸는 함수 본문 (없으면 후보 주변 창) | 판정 대상 코드가 달라졌으므로 재판정 |
| `related_hash` | 팩에 실린 관련 파일(보여 준 앞부분이 아니라 **파일 전체**)과 import 구역(줄 번호를 뺀 정렬한 텍스트) | 판정 근거가 달라졌으므로 재판정 |

규칙의 `title`·`severity`·`message` 는 판정을 바꾸지 않으므로 지문에서 뺍니다 — 제목을 고쳤다고 캐시를 버리지 않습니다. `changed_hunks` 도 뺍니다: 그것은 판정 대상이 아니라 변경 범위를 따라다니는 값입니다.

- 같은 함수가 그대로고 규칙도 그대로면 다시 판정하지 않습니다 — 세션이 달라도 (`verdict_ttl_days` 동안)
- 함수의 **어느 줄이든** 바뀌면 다시 판정합니다. VIOLATION 을 고치려고 반복문 위에 `with()` 를 추가해도 판정이 갱신됩니다
- 팩에 실린 Model 에 relationship 이 추가되는 것처럼 **관련 파일이 바뀌어도** 다시 판정합니다. 리뷰어가 그 내용을 읽고 판정했기 때문입니다. 팩에 보이지 않은 뒤쪽(예: 75행의 `$with`)이 바뀌어도 마찬가지입니다. 파일 맨 위에 주석을 넣어 import 줄 번호만 밀린 경우는 재판정하지 않습니다
- 규칙의 instruction 이나 detect 를 고치면 그 규칙의 기존 판정은 재사용되지 않습니다
- 같은 파일의 다른 함수, 팩에 실리지 않은 파일이 바뀌는 것은 영향이 없습니다

캐시와 판정 배치는 플러그인 데이터 디렉터리의 상태 저장소(`convention-guard.db`, sqlite)에 있고 레포에 커밋되지 않습니다. 판정을 기록할 때 그 레포의 TTL 지난 항목을 지우고, 기록마다 트랜잭션 하나라서 동시에 기록하는 리뷰어끼리 서로의 판정을 덮지 않습니다. 리뷰어 서브에이전트는 플러그인 환경 변수를 물려받지 않으므로, 배치는 저장소 경로를 담은 참조 한 문자열(`<db 경로>#<id>`)로 넘깁니다. 모델의 의견은 팀 결정이 아니기 때문입니다. 팀이 합의한 예외는 `dismiss.py` 로 기각합니다.

## 검증 사이클과의 관계

| 상황 | 동작 |
|---|---|
| 리뷰어가 VIOLATION → 에이전트가 고침 → 함수 본문이 바뀜 | fixed 로 기록하고, 바뀐 함수는 한 번 더 판정 요청 |
| 리뷰어가 VALID | 다음 Stop 에서 제외 — 통과 |
| 판정 요청을 실행하지 않음 (기록 없음) | "실행되지 않았습니다" 로 한 번 더 요청, 그다음은 기록만 남기고 종료 |
| `max_verify_attempts` 소진 | 남은 판정 대기 후보를 `review_skipped` 로 기록하고 종료 |
| `mode: report` | 판정을 요청하지 않음 (차단할 수 없으므로). `review_skipped` 기록 |

## 파일 글롭 상시 판정

정규식으로 후보를 좁힐 수 없는 컨벤션이 있습니다. "컨트롤러에 비즈니스 로직 금지"에는 `if`·`foreach` 처럼 정상 코드에도 있는 모양밖에 없고, 계층 경계는 import 이름(`@/core/OrderStore`)에 infra·db 같은 단어가 없으면 게이트를 그냥 지나갑니다. 이런 규칙은 게이트 대신 파일 글롭을 정하고, 그 파일에 에이전트가 코드를 추가하면 항상 판정합니다. 정규식 신호가 확실한 규칙은 지금처럼 게이트를 씁니다. 그쪽이 더 정확하고 쌉니다.

```yaml
applies_to:
  stacks: [laravel]
  files: ["app/Http/Controllers/**/*.php"]      # 필수
detect:
  when_code_added: true
semantic_review:                                # 필수
  context: [imports]
  instruction: |
    질문은 하나입니다: 이 판정 단위가 컨트롤러에 비즈니스 로직을 들여오는가?
    VIOLATION: 분기로 값을 정함, 가격 계산, 모델 직접 조회·저장 ...
    VALID: 검증, 서비스 호출, 응답 반환. 판단이 서지 않으면 VALID 입니다.
```

질문은 규칙 하나에 대해서만, 좁게 씁니다. "이 diff 에서 문제를 찾아라" 같은 열린 질문은 오탐을 늘립니다.

**판정 단위** — 줄마다가 아니라 단위마다 질문 하나입니다.

| 단위 | 범위 |
|---|---|
| 함수 | 추가된 줄을 감싸는 가장 바깥 함수·메서드. 클로저와 화살표 함수는 바깥 메서드에 합칩니다 |
| 파일 머리 | 함수 밖에 추가된 줄(import, namespace, 클래스 선언, 프로퍼티)을 파일마다 하나로 모읍니다. 함수 본문을 접은 파일 골격을 보여 줍니다 |
| 파일 전체 | 구조 엔진이 없거나 파일을 끝까지 읽지 못했을 때(구문 오류 포함). `함수 경계 미확인` 으로 표시합니다 |

- 글자나 숫자가 있는 추가 줄이 하나 이상 있어야 단위가 됩니다. 닫는 괄호나 빈 줄만 바뀐 레거시 함수는 판정하지 않습니다
- 단위의 코드가 그대로면 캐시된 판정을 씁니다. 단위 안의 어느 줄이든 바뀌면 다시 판정합니다
- 한 번에 규칙당 50개 단위까지 모읍니다. 넘으면 "<규칙>: 판정 단위가 상한 N개에 닿아 나머지는 이번에 판정하지 못했습니다"로 알립니다 (`scan.py --max-hits` 가 50 보다 크면 그 값이 상한)
- `once_per_session` 은 이 규칙에 적용하지 않습니다. 같은 코드를 다시 묻지 않는 일은 판정 캐시가 맡습니다

**재검증 범위** — AI 판정은 결정론이 아니어서, 고칠 때마다 전부 다시 물으면 매번 새 지적이 나와 사이클이 끝나지 않습니다. 그래서 사이클이 열린 뒤에는 이렇게 묻습니다.

| 상황 | 동작 |
|---|---|
| 사이클을 열 때 있던 단위가 아직 판정 전 (다음 묶음) | 묻습니다. 재검증 횟수·연속 차단 횟수에 넣지 않습니다 |
| 수정으로 바뀌거나 생긴 단위(또는 이미 물었는데 import 등 컨텍스트가 바뀐 단위)이고, 그 규칙이 이번 사이클에서 VIOLATION 을 냄 | 다시 묻습니다. 처음 묻는 질문만 있는 차단은 재검증 횟수에 넣지 않습니다. 같은 질문을 두 번 묻는 차단은 셉니다 |
| 위와 같은 단위이고, 그 규칙은 VIOLATION 을 낸 적 없음 | 묻지 않고 "재검증 범위 밖 판정 보류 N"으로 알립니다. 다음 요청에서 판정합니다 |
| 다시 물은 단위가 VIOLATION 이고, 그 규칙이 이미 위반을 낸 파일 | 차단합니다(남음). `max_verify_attempts` 로 제한됩니다 |
| 다시 물은 단위가 VIOLATION 이고, 다른 파일이거나 이번 사이클에서 이미 VALID 판정을 받은 같은 코드 | 차단하지 않고 "보고만 N"으로 알립니다. 다음 요청에서 다시 지적됩니다 |

번들 규칙은 `layering` 프리셋의 `thin-controller`(Laravel 컨트롤러)와 `domain-purity`(`Domain/`·`domain/` 아래)입니다. 글롭에 든 파일에 코드를 추가하는 턴마다 리뷰어 호출이 생기므로 명시해야 켜집니다: `presets: [auto, layering]`.

## 규칙 작성

```yaml
detect:
  when_line_added: '\bforeach\s*\(|->each\s*\('     # 게이트: 좁을수록 싸다
semantic_review:
  context:
    - current_function
    - related_files: {symbol: '\b([A-Z]\w+)::(?:query|with|where)\b', glob: 'app/Models/{1}.php', max: 2}
  max_context_lines: 150
  instruction: |
    VIOLATION: 로드되지 않은 관계에 반복문 안에서 접근한다.
    VALID: 이미 with()/load() 로 로드됐거나 관계 접근이 없다.
    판단할 수 없으면 VALID 입니다.
```

- instruction 에 VIOLATION/VALID 조건을 한 문장씩, 그리고 "판단할 수 없으면 VALID"
- "레포 구조를 훑어보라" 같은 지시는 넣지 않습니다. 팩으로 판정할 수 없는 규칙은 지침(AGENTS.md)으로 남깁니다
- 픽스처는 게이트만 검사합니다

## 비용과 한계

- 판정은 후보가 있는 턴에만, 캐시에 없는 코드에만 발생합니다. 게이트가 넓으면 비용이 커지므로 `log_report.py` 의 정밀도(리뷰어가 VIOLATION 으로 판정한 비율)가 낮은 규칙은 게이트를 좁힙니다. `VALID` 가 많으면 게이트가 넓은 것이고, `FALSE_POSITIVE` 가 많으면 게이트가 엉뚱한 코드를 잡는 것이라 조치가 다릅니다
- 메인 에이전트가 판정 요청을 무시할 수 있습니다. 그 경우 한 번 더 요청하고, 로그에 `review_skipped` 로 남습니다
- `scan.py --review` 의 판정은 로컬 판정 캐시에 의존합니다. CI 에는 캐시도 리뷰어도 없으므로 CI 에서 판정을 기대하지 마세요. 대신 `--review --fail-on-pending` 을 붙이면 판정이 남은 후보가 종료 코드 1 이 되어 "판정 못 함"이 통과로 읽히지 않습니다 ([cli.md](cli.md#ci-에-넣기))
