# 규칙 개선 사이클

규칙은 만드는 것보다 **지우는 것**이 어렵습니다. 수정률이 낮은 규칙을 방치하면
에이전트가 reason 전체를 형식적으로 처리하기 시작하고, 그때부터는 건강한 규칙까지 같이
무시됩니다. 이 스킬은 그걸 막기 위한 정기 점검입니다.

## 1. 건강도 보기

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/log_report.py"
```

로그가 비어 있으면 `CLAUDE_PLUGIN_DATA` 경로가 다른 것입니다. `--log <경로>` 로 지정하세요.

핵심 지표는 **수정률** — 지적한 뒤 다음 턴에 그 지적이 실제로 사라진 비율입니다.

| 판정 | 뜻 | 할 일 |
|---|---|---|
| 건강함 (≥70%) | 지적하면 고칩니다 | `warn` 이면 `error` 승격 검토 |
| 조건 검토 (30~70%) | 절반은 오탐이거나 상황에 따라 다름 | 조건을 좁힐 수 있는지 확인 |
| 오탐 의심 (<30%) | 지적해도 아무도 안 고칩니다 | 좁히거나 지우기 |
| 데이터 부족 (<3회) | 판단 불가 | 그대로 두기 |

**수정률이 낮다고 바로 지우지 마세요.** 두 가지 원인이 섞여 있습니다.

- 오탐 → 조건을 좁힙니다
- 팀이 그 규칙에 동의하지 않음 → 지웁니다

## 2. 원인 구분하기

낮은 규칙마다 실제 사례를 보세요. 리포트가 "자주 걸린 파일"을 알려줍니다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scan.py" --all --rule <규칙-id> --no-color
```

걸린 위치를 서너 개 `Read` 로 열어 확인하세요.

- **정상 코드가 걸림** → 오탐. 3번으로.
- **진짜 위반인데 안 고침** → 팀이 동의하지 않거나, 고치는 비용이 큽니다.
  사용자에게 물어보세요. "이 규칙 유지할까요, 강도를 내릴까요, 지울까요?"
- **특정 디렉터리에만 몰림** → 규칙 문제가 아니라 그 구역이 레거시입니다.
  규칙을 건드리지 말고 `exclude` 에 경로를 추가하세요.

## 3. 조건 좁히기

정규식을 고칠 때는 **반드시 픽스처를 먼저 추가**하세요. 오탐 사례를
`should_not_match` 에 넣고 그게 통과하도록 정규식을 고치는 순서입니다. 반대로 하면
같은 오탐이 다시 돌아옵니다.

```yaml
tests:
  should_not_match:
    - '이번에 오탐으로 걸렸던 실제 코드 한 줄'
```

토스 사례처럼 공백 하나로 끝나는 경우가 많습니다. 정규식을 통째로 다시 쓰기 전에
경계 조건(`\b`, 앞뒤 문자 제한, 룩비하인드)부터 검토하세요.

줄 단위로는 도저히 안 되겠다면 트리거 종류를 바꾸는 것도 방법입니다 —
파일 맥락이 필요하면 `when_line_added` + `must_contain_in_file`,
의미 판단이 필요하면 `review_when` + `review_prompt`.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/test_rules.py"
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scan.py" --all --rule <규칙-id> --no-color
```

고치기 전후의 건수를 비교해서 보고하세요.

## 4. 강도 조정과 승격

- **승격** (`warn` → `error`): 수정률 70% 이상 + 발동 10회 이상일 때만.
- **강등** (`error` → `warn`): 오탐이 남아 있는데 작업을 막고 있을 때.
  공통 규칙이면 레포 config 의 `severity:` 로 내리세요. 그러면 로그에 `downgraded` 로
  남아서 나중에 볼 수 있습니다.
- **삭제**: 팀이 동의하지 않는 규칙. 지우기 전에 사용자 확인을 받으세요.

레포 로컬에서 조정할 때:

```yaml
# .claude/convention-rules/config.yaml
severity:
  core/php-line-too-long: warn      # 승격
disable:
  - core/js-no-console              # 이유를 주석으로 남길 것
exclude:
  - "legacy/**"
```

## 5. 새 규칙 후보 찾기

로그에는 "무엇을 놓쳤는지"가 없습니다. PR 리뷰 코멘트가 그 자리를 채웁니다.
최근 리뷰에서 같은 지적이 세 번 이상 반복됐다면 규칙 후보입니다 —
`rule-add` 스킬로 넘기세요.

```bash
gh pr list --state merged --limit 30 --json number,title
gh pr view <번호> --comments
```
