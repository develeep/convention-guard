# 규칙 개선 사이클

수정률이 낮은 규칙을 방치하면 에이전트가 차단 메시지 전체를 형식적으로 처리하기 시작하고, 그때부터는 건강한 규칙까지 함께 무시됩니다.
판단은 숫자로 합니다. "좋아 보인다"로 결정하지 않습니다.

## 체크리스트

```
- [ ] 1. 건강도 보기
- [ ] 2. 판정별로 원인 확인
- [ ] 3. 조건 좁히기 (픽스처 먼저)
- [ ] 4. 강도·모드 조정
- [ ] 5. 정리하고 보고
```

### 1. 건강도 보기

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/log_report.py" --repo . --since 21
```

비어 있으면 훅이 아직 돌지 않았거나 로그 위치가 다릅니다 (`--log <경로>`, userConfig `log_dir`).

| 열 | 뜻 |
|---|---|
| 후보 | 이 규칙이 찾은 서로 다른 후보 수 |
| 고침 / 남음 | 지적된 뒤 검증 사이클이 닫힐 때 사라졌는지 / 남았는지 |
| 기각 | 오탐으로 기록된 수 — 오탐의 직접 증거 |
| 신규 | 다른 지적을 고치다가 이 규칙을 새로 어긴 수 |
| 수정률 | 고침 / (고침 + 남음) |
| 정밀도 | 의미 판정 규칙(*)에서 리뷰어가 VIOLATION 으로 판정한 비율 |

리포트 아래 "의미 판정 내역" 표는 리뷰어 판정을 셋으로 나눠 보여줍니다. 둘 다 위반은 아니지만 조치가 다릅니다.

| 판정 | 뜻 | 조치 |
|---|---|---|
| `VALID` | 게이트는 적절했고 그 코드가 정상이었다 | 게이트가 넓음 — `detect` 를 좁혀 판정 비용을 줄임 |
| `FALSE_POSITIVE` | 게이트가 애초에 엉뚱한 코드를 잡았다 | `detect` 정규식이 틀림 — 3단계로 픽스처부터 고침 |
| `VIOLATION` | 실제 위반 | 정밀도의 분자 |

### 2. 판정별로 원인 확인

| 판정 | 먼저 볼 것 | 보통의 조치 |
|---|---|---|
| 오탐 확정 (기각 ≥ 절반) | 리포트의 기각 사유, `dismiss.py --list` | 3단계로 조건 좁히기 |
| 게이트가 넓음 (정밀도 < 20%) | 리뷰어가 VALID 로 판정한 후보들 | `detect` 게이트 좁히기 — 판정 비용이 매번 나가는 중 |
| 게이트가 엉뚱함 (게이트 오탐률 ≥ 50%) | 리뷰어가 FALSE_POSITIVE 로 판정한 후보들 | 그 코드를 `tests.no_match` 에 넣고 3단계로 정규식 수정 |
| 수정이 새 위반을 만듦 | 신규 위반 위치 | `message` 의 수정 지침을 구체적으로 |
| 오탐 의심 (수정률 < 30%) | `scan.py --all --rule <id>` 로 실제 사례 서너 개 `Read` | 정상 코드가 걸림 → 3단계 / 진짜 위반인데 안 고침 → 사용자에게 유지·강등·삭제 질문 |
| 조건 검토 (30~70%) | 같음 | 상황에 따라 다른지 확인, 경로로 나뉘면 `exclude` |
| 건강함 (≥ 70%) | — | 4단계에서 승격 검토 |
| 데이터 부족 | — | 그대로 둠 |

지적이 특정 디렉터리에 몰리면(리포트의 "자주 걸린 파일") 규칙 문제가 아니라 레거시 구역입니다. 규칙은 두고 레포 config 의 `exclude` 에 경로를 넣습니다.

### 3. 조건 좁히기 — 픽스처 먼저

순서를 지킵니다. 반대로 하면 같은 오탐이 다시 돌아옵니다.

1. 오탐이었던 실제 코드 줄을 `tests.no_match` 에 추가합니다. `dismissed.yaml` 항목의 주석에 원래 코드가 남아 있습니다.
2. 픽스처를 돌려 **실패하는 것을 확인**합니다.
3. 정규식을 좁힙니다. 통째로 다시 쓰기 전에 경계(`\b`, 앞뒤 문자, 룩어헤드)부터 봅니다.
4. 통과할 때까지 2–3 을 반복합니다.
5. 전후 건수를 비교합니다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/tests/rules/test_rule_fixtures.py" --repo .
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/scan.py" --all --rule <id> --no-lint --fail-on never --no-color
```

core 규칙은 레포에서 `override: core/<id>` 파일로 좁힙니다 (형식: rule-add 스킬의 references/schema.md).
줄 하나로는 판정이 안 되면 앵커를 바꿉니다: 파일 맥락이 필요하면 `must_contain_in_file`, 의미가 필요하면 `semantic_review`.

### 4. 강도·모드 조정

| 조치 | 조건 |
|---|---|
| warn → error 승격 | 수정률 ≥ 70%, 고침+남음 ≥ 10, 기각 사유가 반복되지 않음 |
| error → warn 강등 | 오탐이 남아 있는데 작업을 막고 있음 |
| 삭제 (`disable` + 이유 주석) | 팀이 동의하지 않음 — **사용자 확인 후** |
| `mode: report` → `fix` | 차단 강도 규칙이 모두 건강함 또는 데이터 부족 |

레포 config (`.claude/convention-guard/config.yaml`)의 `severity:` 로 조정하면 로그에 base 강도가 남아 나중에 추적됩니다.

### 5. 정리하고 보고

좁혀서 더 이상 걸리지 않게 된 기각 항목은 `dismissed.yaml` 에서 지웁니다. 남겨두면 다음 점검에서 규칙이 실제로 좁혀졌는지 판단하기 어렵습니다.

```
기간: 최근 21일 · 이벤트 1,204건
손본 규칙:
- core/next-no-public-secret: 기각 5건(공개 키) → no_match 3개 추가, _KEY 대안 제거 · 전수조사 41→3건
승격: core/laravel-controller-needs-validation warn→error (수정률 86%, 14건)
보류(데이터 부족): core/go-wrap-error, core/react-no-index-key
모드: report 유지 — laravel-no-query-in-blade 수정률 41%
새 규칙 후보: PR 리뷰에서 "DTO 없이 배열 반환" 지적 4회 → rule-add
```

새 규칙 후보는 로그에 없습니다. 최근 PR 리뷰에서 같은 지적이 세 번 이상 반복됐는지 `gh pr view <번호> --comments` 로 확인하고 rule-add 로 넘깁니다.
